# ADR 0007: SEP-10 for Anchor Authentication vs SEP-45 Consideration

## Status
Accepted

## Context
The backend needs to authenticate with anchors to perform SEP-24/SEP-6 deposit and withdrawal flows. The Stellar ecosystem provides two authentication mechanisms:

1. **SEP-10**: Web Authentication standard that uses signed transactions as proof of wallet control
2. **SEP-45**: Standardized stellar.toml-based authentication (future mechanism)

This decision documents why we chose SEP-10 for the current anchor integration.

## Decision
Implement SEP-10 for anchor authentication. This involves:
- Requesting a challenge transaction from the anchor's AUTH_SERVER
- Validating the challenge structure (source account, manage_data operation, timebounds)
- Signing the challenge with the sponsor account
- Submitting the signed challenge to get a JWT token
- Caching the JWT until expiration
- Using the JWT token for authenticated anchor API calls

## Rationale

### Why SEP-10 (chosen)
1. **Currently Standard**: SEP-10 is the established, widely-adopted authentication method for Stellar anchors
2. **Proven**: Used by existing anchors and SEP-24/SEP-6 implementations
3. **Simple Implementation**: Challenge-response mechanism is straightforward to implement
4. **Account Verification**: Proof of wallet control is built into the protocol
5. **Stateless**: No persistent state needed beyond JWT caching
6. **Compatible**: Works with all current licensed anchors

### Why Not SEP-45 (yet)
1. **Future Standard**: SEP-45 is not yet finalized or widely adopted by anchors
2. **Unclear Adoption**: Limited implementation examples available
3. **Risk**: Switching protocols later would require code changes and testing
4. **Timing**: Too early for production reliance; SEP-10 is the current requirement

## Implementation Notes

### SEP-10 Client Responsibilities
- **Challenge Request**: Fetch challenge from anchor's AUTH_SERVER
- **Challenge Validation**: Verify source account, operations, and timebounds
- **Challenge Signing**: Sign as the sponsor account (the signer of the transaction)
- **Token Submission**: Submit signed challenge to get JWT
- **Token Caching**: Cache JWT with TTL until expiration
- **Error Handling**: Clear error codes for validation failures

### Challenge Validation Checklist
- [ ] Source account matches sponsor
- [ ] Contains at least one manage_data operation for the wallet
- [ ] Transaction timebounds are valid (not expired, not in future)
- [ ] Network passphrase matches (TESTNET or PUBLIC)

### Anchor Discovery (SEP-1)
Before SEP-10 auth, discover anchor endpoints:
- Fetch stellar.toml from anchor domain
- Validate and cache TOML with TTL
- Extract AUTH_SERVER and TRANSFER_SERVER URLs

## Migration Path

If SEP-45 becomes standardized and adopted:
1. Create Sep45Client implementation (similar to Sep10Client)
2. Add anchor configuration to choose protocol version
3. Implement fallback mechanism (try SEP-45, fall back to SEP-10)
4. Deprecate SEP-10 when all required anchors support SEP-45

## Testing

Tests cover:
- Challenge structure validation
- Timebounds checking (past, present, future)
- manage_data operation validation
- JWT token parsing and caching
- Timeout handling
- Error cases (bad challenge, network errors)
